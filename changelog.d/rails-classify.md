### Added

- `zigapagos migrate` now classifies every route Stage 2 recovers into one of `content`, `island`, `backend`, `redirect`, or `unresolved`, and prints the verdict (`` — content ``, `` — backend ``, ...) after each rendered route line, plus a summary table (`## Routes`'s `| Class | Count |`) totaling the whole route set. Classification joins three sources of evidence: the route's HTTP verb, its resolved view template AND everything that template pulls in (its resolved layout, by convention, plus any partial it or the layout renders, followed transitively up to a bounded depth — engine + a text scan for request-time state, Stimulus, and mounted-component markers, merged across every file visited), and controller-action shape read from a static Prism AST walk (whether an action's body is only `redirect_to`, whether it ever `render json:`s outside a `respond_to` HTML branch). Rules apply in a fixed, spec-defined order — a non-GET verb is always `backend`; a route with no view template AND (an action that renders JSON, or no recovered action at all — while controller-shape discovery succeeded) is `backend`; a pure-redirect action is `redirect`; a non-`erb` template (Haml, Slim, jbuilder, builder, or an engine that could not be identified) is `unresolved`; a view (or its layout, or a rendered partial) reading request-time state (`current_user`, `session`, `params`, `flash`, `cookies`, `policy(`/`can?`, CSRF helpers, and related patterns) is `unresolved`; a view wiring up a Stimulus controller or mounting a JS component root is `island`; anything left over — a view with no negative evidence, a recovered action confirming it, and every `render` target the transitive scan followed successfully — is `content`, the only verdict this stage asserts positively. A `render` target the scan cannot resolve (a dynamic expression, a literal matching no known template, or nesting past the followed depth) is evidence not in hand, so that route may reach every verdict above except `content`.
- The sixth value, `spa`, is declared in the classification vocabulary but this stage assigns it to nothing: telling a component-root marker apart from a component that merely renders inside a larger page needs the component's module and its imports resolved, which is out of scope here. A mounted component root classifies `island` today rather than a guessed `spa`.

### Known limitations

- The transitive template scan resolves the layout and partials by Rails' PATH CONVENTION, not by reading a controller's `layout` declaration (out of scope for this stage) — right for the overwhelming majority of apps, but a controller that overrides its layout dynamically (`layout :choose_layout`) is read as if it used the conventional one. Partial nesting is followed up to a bounded depth (`RAILS_TEMPLATE_RENDER_DEPTH_EXCEEDED` names it when hit) rather than indefinitely.
- Classification depends on the controller-analysis sidecar succeeding AT ALL. When it can't run (no Ruby, no sidecar script, a spawn/response failure) or `app/controllers/` is missing entirely, no verdict rests on an absent action (that would be the same non-signal for every route in the app) and every affected route lands on `unresolved` naming the missing evidence. A run where controller analysis SUCCEEDED but simply never found one particular route's action still classifies that route `backend`/`unresolved` as before — only the wholesale-failure case is gated.
- This is per-route, per-run classification only: there is no versioned, machine-readable manifest yet, no JSON Schema, no drift gate, and no `--strict` mode that fails a run on `unresolved` routes. Those are Stage 4.
- Nothing in the classifier itself assembles a migration target, and `--copy-assets` is rejected outright for Rails sources. The `--target` conversion added later in this release does the assembling — see `docs/migration/rails-to-zigapagos.md` and its `skills/` mirror.
- The classifier only detects and defers: it does not propose a resolution for a page classified `unresolved` for request-time state (`current_user`, `session`, ...). What that page should become is a `findings[]` question with an explicit set of choices, answered in `MIGRATION.decisions.json` — and a route can classify `unresolved` here and still convert cleanly, because the two are different claims.
