### Added

- **`zigapagos migrate <rails-app> --from rails --target DIR --backend openapi.json` now binds a Rails app's mutations to a ZigBase contract.** `openapi.json` is the document `zigbase openapi` writes (OpenAPI 3.1.2, `x-zigbase-access`/`x-zigbase-auth`, `list|create|view|update|delete<Base>` operation ids); the flag is Rails-only, has **no default location** — a document the operator did not name is a document the run does not have — and is read for two things: the `choices` a `RAILS_BACKEND_ENDPOINT` finding offers, and the auth collections a `RAILS_AUTH_JOURNEY` answer is validated against. Without it those findings offer nothing but `retain`/`blocked`, so a backend route can be acknowledged but not bound, exactly as before. The document is an INPUT: it is never copied into the target, and the handoff records only its basename and contract version.
- `RAILS_BACKEND_ENDPOINT` now covers **three** shapes with one code and offers real answers to all of them: a `form`/`form_field` region, a `link_to`/`button_to` that performs a mutation, and a non-GET or JSON-rendering route. Its `choices` are the document's own operation ids, filtered to the finding's own verb (**a different verb is never offered**, which is what stops an operator binding a `DELETE` link to `createPosts`) and ranked with the finding's own resource first. `custom:/<path>` is additionally accepted — an absolute path, no whitespace, no quotes — for a consumer route the document does not describe; it is deliberately not enumerated in `choices`, because a free-form token cannot be, and the finding's own `message` says so.
- The route-level shape of that code is the **one** row that does not fold a whole `routes.rb` line into a single question. `resources :posts` declares `POST /posts`, `PATCH /posts/:id` and `DELETE /posts/:id` on one line and no single ZigBase operation serves all three; `resources :posts, :comments` puts two resources on one line and `createPosts` cannot serve a comment. So the row groups by `(line, verb, resource)` and carries both in its id — `RAILS_BACKEND_ENDPOINT.config/routes%2Erb.L20.GET.posts`. The `resource` component is always emitted (empty when the controller never resolved) so a reader never has to guess whether a trailing token is a verb or a controller.
- **An answered finding produces a working island, not a note.** The bound region is replaced by `<island src="components/forms/<view stem>.island.tsx" client:load>` — no `rails:finding` marker, no placeholder — and the target gains that `.tsx`, a `lib/zb.ts` (`createClient("", { authStore: new LocalAuthStore() })`), a `"@zigbase/client": "0.3.0"` dependency and one `--island=` flag in `build.sh`. Which client call the island makes is read off the verb and the collection, because the document is the authority on both: `create(values)` / `update(values.id, values)` / `delete(values.id)` on a collection operation, `zb.send("<VERB>", "<path>", { body: values })` on a consumer route or a `custom:` answer. The redirect after a successful submit is the **paired** Rails action's own `redirect_to`, resolved through the route table (`C#new` → `C#create`, `C#edit` → `C#update`); an unresolvable one becomes `setDone(true)` rather than a guessed URL. A form that updates or deletes a record with no `id` field renders `TODO: this form acts on one record; pass its id` and nothing else — a submit that can only fail at runtime is worse than an honest stub. Every island carries a header comment naming the exact ERB it replaced and stating that enforcement stays server-side.
- **Validation errors are rendered where the ERB rendered `full_messages`.** An `errors` summary naming the bound form's own model (`@post.errors` beside `form_with model: @post`), or any summary in a template whose bound form declares no model, is absorbed into that form's island and emits no region of its own — the island renders `ZigbaseError.data`'s field errors in that position. That also closes one instance of issue #181 by construction: the `full_messages.each do |m|` block local no longer reaches the converter, so it can no longer become an id-less `<!-- rails:unmapped local -->` that no decision could name. A summary naming a *different* model is untouched.
- **`RAILS_AUTH_JOURNEY`** folds a whole sign-in/sign-up flow into one question, keyed on the smallest `config/routes.rb` line any journey route was declared on, because the answer to both halves is a single ZigBase auth collection. A route is a journey route when its controller is `sessions`/`registrations` or its own reachable view holds a form with a `password_field`; journey views — and, through the render graph, the partials they render — raise no `RAILS_BACKEND_ENDPOINT` of their own, so one form cannot collect two conflicting answers. It is the first finding with `requires_artifact: true`, and the artifact is validated: an auth collection is the one whose create schema carries **both** `password` and `passwordConfirm` (the only marker the document has), and any other name is refused with the allowed list. One `island` answer scaffolds `components/AuthForm.island.tsx` (ONE component for both halves, told apart by a `mode` prop, each redirecting where its Rails action did), `components/AuthStatus.island.tsx` for the `current_user` regions, `lib/zb.ts` with `authCollection` set, and the journey's three endpoints — `authWithPassword`, `logout`, `createUsers`. The first two are `CollectionService` *method* names rather than operation ids because `x-zigbase-coverage.allAuthMethods` is always false: `auth-with-password` and `auth-logout` are not in the document at all, and `createUsers` is re-derived by ZigBase's own `<verb><Base>` rule so all three come from one rule rather than a trio that would disagree with itself the moment the document changed.
- `AuthStatus` renders the signed-out branch on the server and flips after hydration (`useEffect(() => setReady(true), [])`): the session lives in the visitor's own browser, so reading the store during the first render would make the server's markup and the client's disagree. Two rules govern how often it mounts. A **complementary pair** in one template — `<% if current_user %>…<% end %>` beside `<% unless current_user %>…<% end %>` on the same predicate, either polarity, `!`/`not` included — is ONE control and mounts once, with the absorbed half named in the route's note; two regions of the same polarity, two regions on different predicates, and the same pair in two templates are all two controls and mount twice, because a duplicate is a visible blemish while a wrong pairing silently *deletes* a control. And the "Sign in" link is the journey's own `sessions#new` route path: a journey detected only by a `password_field`, with no `sessions` controller, renders **no link** rather than one to a URL that does not exist.
- **A mutating `link_to`/`button_to` is no longer a link.** Unanswered it is an empty `rails:finding` region and its page stays `open`; answered it is a click island with the control's own text, its `data-confirm`/`data-turbo-confirm` guard, and the *mutating* action's redirect. Before this, such a node converted to `<a href="/logout" method="delete">` — an ordinary GET link pointing at a `DELETE` route — on a page the handoff reported `migrated` with nothing open. The verb is read from `method:`, Turbo's `data-turbo-method`, rails-ujs's `data-method`, or `button_to`'s POST default, and an explicit `get` on any of them answers "not a mutation" so an ordinary navigation link is untouched.
- The Ruby sidecar now flattens nested `data:`/`aria:` option hashes the way ActionView's own `tag_options` does — `data: { turbo_method: :delete }` → `data-turbo-method="delete"`, in the hash's own position among the options, values rendered as Rails renders them, `nil` pairs skipped — and lifts `button_to`'s `form: { data: … }` onto the control, since Turbo consults the form's `data-turbo-confirm` exactly as the submitter's. Before this, `link_to "Sign out", logout_path, data: { turbo_method: :delete }` collapsed to the sentinel `data="{...}"`, raised no finding at all, and shipped a GET link to a DELETE route; a `button_to` carrying `form: { data: { turbo_confirm: … } }` was worse still — the nested hash made the whole call `route_helper_dynamic`, so a mutating control produced no finding of any kind.
- **`RAILS_ROUTE_AUTH_GUARD`** (new code, new choice word `public`) asks about a page route whose controller — **or a class it inherits from** — runs a `before_action` whose symbol name contains `login`, `auth`, `sign` or `user` and does not `skip_before_action` it. A static page cannot enforce the guard, and shipping it silently public is exactly the "silently marked complete" this migration refuses. The chain walk is the point: the overwhelmingly common Rails shape is one `before_action :authenticate_user!` on `ApplicationController` with everything else inheriting it, and matching only the route's own controller found nothing. `public` means "ship the page; the ZigBase rule on the operation protects the data" and records itself in the route's note (`guarded by before_action :require_login; shipped public by decision`); the message names the *declaring* controller, and picks the smallest `(name, line)` among matches so it does not depend on the order the sidecar's directory walk emitted the filters in.
- **`RAILS_CONTENT_PATH_COLLISION` and `RAILS_ROUTE_PATH_UNSUPPORTED`** (issue #182): the two route-level open notes that carried no finding id — "content path collision with GET /about" and "route path contains syntax this stage does not interpret" — are now answerable findings keyed on the `routes.rb` line, `retain`/`blocked`, derived from the same claim walk the converter itself uses so the finding and the note cannot disagree.
- The handoff's `backend` object and `routes[].endpoint` are filled for the first time: `{"file": "openapi.json", "contract_version": "1.0.0"}` (the basename, because a committed artifact must not carry the operator's directory layout) and `{"operation_id", "verb", "path"}` taken from the **document**, not from the Rails route — `GET /feed` answered `listPosts` records `/api/collections/posts/records`. An endpoint arrives three ways: a route-level answer fills its own route, a form answer fills the non-GET route its `new`/`edit` action pairs with, and a link answer fills the route the link names outright. `MIGRATION.md`'s `## Handoff` section gains two unconditional lines, `backend: openapi.json (1.0.0)` (or `backend: none`) and ``endpoints: N of the M `backend` route(s) are bound to a ZigBase operation``. `backend: none` does not disappear when the flag is absent: the operator wondering why their findings offered nothing but `retain`/`blocked` is precisely the operator who forgot it.
- `redirects[].to` is now the target the redirecting action names, resolved through the route table (`redirect_to about_path` → `/about`). It stays `null` for a target this run cannot resolve — a `redirect_to @post`, a `redirect_back` — and the row then says `redirect target is request-time state; set it by hand`, which is the only place an operator learns the host-config stanza is incomplete.

### Changed

- **`complete` no longer accepts a `backend` route on the strength of its status alone.** A `backend` row counts as accounted only with a non-null `endpoint` **or** a non-null `decision`. Non-GET/HEAD routes stay outside the count entirely, so this bites on exactly one shape — a user-facing GET that renders JSON — which is the shape where the old rule let a route the operator had never been asked a question about look finished. The `rails-convert.md` fragment earlier in this same release states the previous rule (`migrated`, `redirect`, `backend`, or `retained`/`blocked` with a decision); it has been corrected alongside this one rather than left to publish a contradiction, as that fragment itself did for `rails-target.md`.
- **A singular Rails `resource` routes to the PLURAL controller.** `resource :session` is `SessionsController`, not `SessionController` — `ActionDispatch`'s `SingletonResource#controller` is `options[:controller] || name.to_s.pluralize` — while the path and every route-helper name stay singular. The sidecar now pluralises with an order-preserving port of `ActiveSupport::Inflector`'s own plural rules (uncountables included: `resource :series` is `SeriesController`), cross-checked against live activesupport over forty words with zero mismatches. This was not a cosmetic label: a route whose controller does not resolve reaches no template, so it raised no finding from that template and produced no page — an app's entire sign-in flow was invisible to the migration, and the auth-journey detection above could never fire on an idiomatic app. Closes **#176**, and withdraws the guide's advice to write `controller:` on every singular `resource`, a workaround real Rails apps do not carry.
- **The `@z/runtime` dependency defaults to `ZIGAPAGOS_RUNTIME_DIR`** when `--runtime-path` was not given (issue #179). That is the same variable the Rails sidecar and both bundlers already need when `zigapagos` is driven out of a checkout, so in that setup the generated `package.json` is written resolved with nothing extra to remember. `--runtime-path` still wins; with neither, the `file:TODO-SET-RUNTIME-PATH` placeholder is unchanged. It now matters on far more runs than before, because every `--backend` binding emits a `package.json` where previously only a `spa` answer did.
- An unusable `--backend` or `--decisions` **path** now prints `error: <flag> <path> could not be read: <OS error>` and exits **1**, instead of taking the fatal path — which panics under a debug build, and a debug build is what every shell e2e drives, so all four failure shapes (missing, a directory, unreadable, over the 16 MiB cap) arrived as exit 134. A path the operator typed wrong is their input being wrong, the same class as an unusable decisions file. The message names the flag as well as the path, because the two fail identically at the OS level and an operator who passed both needs to know which one the kernel refused.
- `--doctor`'s mutual-exclusion message lists `--backend`.
- **Every answer on a route is applied, strongest first**, rather than only the one the rank picks. Each answered finding is settled by its own choice and the route's status is the strongest outcome among them, so a route carrying both a bound mutation and an answered `RAILS_ROUTE_AUTH_GUARD` comes back `migrated` **with** `guarded by before_action :require_login; shipped public by decision` on it. Applying one answer per route would have meant an operator who answered every question on a route still could not close it: the binding and the `public` both rank as producing, and `RAILS_BACKEND_ENDPOINT.<view>…` sorts before `RAILS_ROUTE_AUTH_GUARD.config/…`. `retain` and `blocked` acknowledge the route rather than anything on it, so they stop the walk: they are the top two ranks and can only ever be the first answer applied, and carrying on past one would file notes about work that is not happening (`public`'s note claims a guarded page is shipping; on a retained route no page ships). Three arms sit outside the rule and apply one answer each: a dynamic route looks up the answer to the `RAILS_ROUTE_DYNAMIC_SEGMENT` id it just raised rather than choosing among the route's findings, and a `redirect` or `backend` route records its own answer — a backend route that bound an endpoint also settles it — without letting it change the route's status (both are already complete answers about what the route is).
- **A finding inside a region an island replaced is settled, not refused.** A sign-out `button_to` inside an `if current_user` region is answered by construction when `AuthStatus` replaces that region, so the fixture leaves it unanswered — but an operator who answers it *as well* gets it accepted and settled, with the route's `note` naming both ids (`choice … superseded by the island answering …, which replaced the region it sits in`). Rejecting it would have exited 3 with `choice custom:/… needs the --backend document that names it` on every page rendering the nav, which is misleading when `--backend` was passed. An answered *status* region nested inside another is additionally marked `enclosed`: the island's header lists it among the regions it replaces (`current_user.email (inside the region above, which this replaces)`) and the route note says ``… `current_user.email` is inside the region the AuthStatus island replaced, so it mounts nothing of its own``.

### Known limitations

- **The literal `backend` choice on `RAILS_REQUEST_TIME_STATE` still has no converter** (issue **#184**). It is a leftover from before this stage and is not the same thing as binding an endpoint: the answer is recorded and the route stays `open` with `choice backend on RAILS_REQUEST_TIME_STATE has no converter (see #184)`. What an operator almost always wants instead is `island` on that region, or an operation id on the `RAILS_BACKEND_ENDPOINT` beside it. The `rails-convert.md` fragment's "Islands and backend endpoints are not produced" bullet has been corrected in place for the same reason as the `complete` rule above.
- **The emitted `tsconfig.json` makes `tsc` report `TS7026` on every island** (issue **#185**) — *JSX element implicitly has type 'any'*. It is a property of the emitted `tsconfig` plus `@z/runtime`'s exports map under `moduleResolution: "bundler"`, not of the generated code: a two-line hand-written island produces it too, and `build.sh` — the real Bun/esbuild pipeline and the SSR sidecar — is green. A consumer who runs `tsc` over the target sees a red tree until it lands.
- **A login partial reached only through the LAYOUT is not the journey's.** Journey membership is seeded from route views and widened through the render graph, so a `shared/_login_form` that only the application layout renders keeps its own `RAILS_BACKEND_ENDPOINT` question rather than being folded into the journey. Answerable, just answerable twice.
- **A form declared in a Rails layout raises its question but cannot be answered into an island** — the layout conversion is passed no bindings, so the region stays a `rails:finding` marker whatever is recorded against it.
- **A nested `data:` hash that does not flatten is noted, never silent.** If the sentinel reaches the converter — which it still can, because `--runtime-path`/`ZIGAPAGOS_RUNTIME_DIR` choose the sidecar and an older one collapses the hash — the island is still written and the binding still stands, with a comment after the `<island>` and a route note reading `nested data: on a bound control was not recovered; a confirm guard may be missing`. Refusing the answer would leave the operator nothing to do but edit the ERB.
- Turbo frames, Turbo streams and React/Vue component roots remain acknowledgeable (`retain`/`blocked`) rather than convertible; `island` on one of those is recorded and leaves the route `open` with `choice island deferred to Stage 4`. `parity[]` is still always empty.
