# `curl | sh` installer

Design, 2026-08-01.

## Problem

Zigapagos ships through two channels today, and neither is the one a reader of
the front page reaches for.

- **npm** (`npx zigapagos`, `npm i zigapagos`) is complete: `@zigapagos/cli`
  bundles the `@z/runtime` tree, depends on Bun, ZigBase and TypeScript, and its
  launcher sets `ZIGAPAGOS_RUNTIME_DIR`. It requires Node.js.
- **The release archives** (`x86_64-linux-musl.tar.xz`, `x86_64-macos.zip`)
  contain the binary and *nothing else* — no runtime tree, no Bun. Islands and
  SPAs, which are the product, do not work from an archive install.

There is no `curl … | sh`, the install method most single-binary tools lead
with. Adding one that only unpacks the existing archive would make the headline
install method the crippled one, so the installer and the missing payload have
to land together.

## What is installed

A *complete* install, equivalent in capability to `npm i zigapagos`, minus the
Node.js requirement.

```
$XDG_DATA_HOME/zigapagos/            (default ~/.local/share/zigapagos)
  versions/<tag>/
    bin/zigapagos                    the release binary
    runtime/                         @z/runtime + sidecar + vendored node_modules
    bun/bun                          only when the host had no bun on PATH
  current -> versions/<tag>          symlink

~/.local/bin/zigapagos               generated POSIX sh shim
$XDG_CACHE_HOME/zigapagos/zigbase/<pinned>/zigbase
                                     the binary's existing cache path, unchanged
```

Nothing is written outside those three roots. No `sudo`, and no edits to shell
startup files.

### The shim

`~/.local/bin/zigapagos` is generated, not copied:

```sh
#!/bin/sh
# generated by the zigapagos installer — do not edit
ZIGAPAGOS_HOME=<data-dir>/current
ZIGAPAGOS_RUNTIME_DIR="$ZIGAPAGOS_HOME/runtime"
export ZIGAPAGOS_RUNTIME_DIR
if [ -x "$ZIGAPAGOS_HOME/bun/bun" ]; then
  PATH="$PATH:$ZIGAPAGOS_HOME/bun"
  export PATH
fi
exec "$ZIGAPAGOS_HOME/bin/zigapagos" "$@"
```

It points at `current`, not at a version directory, so upgrading is one symlink
flip and the shim is never rewritten.

`PATH` is **appended to, never prepended**. This is the same rule
`npm/cli/index.js` documents for its own `.bin` handling: the ZigBase locator's
second step is a `PATH` scan, so a Bun or ZigBase the user put on `PATH`
deliberately must keep winning. The private Bun is a fallback for a host that
had none, not a substitution.

Setting `ZIGAPAGOS_RUNTIME_DIR` in a wrapper rather than in the user's `.bashrc`
keeps the variable scoped to the process that needs it. An exported variable in
a dotfile leaks into every shell, is invisible to non-login shells and CI, and
survives an uninstall.

## The missing payload: a `runtime.tar.xz` release asset

The release publishes one new asset, built by `scripts/pack-runtime.sh` from a
job that has Bun:

- `runtime/src`, `runtime/sidecar`, `runtime/scripts`, `runtime/package.json`,
  mirroring the staging rules in `npm/publish.mjs` — `test/` and `*.test.ts` are
  excluded, because the bun-test suite and its fixtures are not a runtime.
- a vendored `node_modules`, so the install needs no registry contact and cannot
  drift after the release is cut.

`node_modules` is produced in two steps:

1. `bun install --frozen-lockfile --production` — `preact` and
   `preact-render-to-string` at exactly the lockfile's versions.
2. `typescript` installed separately at the range in `runtime/package.json`'s
   dev dependencies.

Two steps because `--production` correctly drops the dev block, and `typescript`
is in it — but `typescript` is not dev-only at run time: the props-check gate
(`--island-props-check`) and the per-SPA runtime slicer both use it, which is why
`@zigapagos/cli` ships it as an optional dependency. Installing it separately is
safe specifically because `typescript` has no transitive dependencies, so the
second step cannot perturb the resolution the first step pinned. The rest of the
dev block (`happy-dom`, `@types/bun`) is test-only and stays out.

**The per-target archives are unchanged.** Adding the runtime to them would
change the shape of an artifact people already extract (today it is a bare
`zigapagos` file), duplicate the tree once per target, and falsify
`tests/meta/runtime-deps-doc.sh`'s assertion that a release archive carries the
binary alone. A separate asset keeps every existing claim true.

## `install.sh`

POSIX `sh` — it is piped to `sh`, so no bashisms. The canonical copy lives at the
repository root.

**Version resolution.** Default is the newest release, resolved from the
`releases/latest` **redirect** (`curl -fsSLI -o /dev/null -w '%{url_effective}'`),
not the GitHub API. The API rate-limits unauthenticated callers to 60/hour per
IP, which for a `curl | sh` behind a corporate NAT is an install that fails for
reasons the user cannot see. `--version vX.Y.Z` / `ZIGAPAGOS_VERSION` overrides.

**Host detection.** `uname -s`/`uname -m` map to `x86_64-macos` or
`x86_64-linux-musl`. Every other host is **refused**, reusing the wording
`npm/cli/index.js` already prints:

- aarch64 (Linux and macOS alike): `zig translate-c` SIGSEGVs on the wuffs
  dependency for every aarch64 target on released Zig 0.16.0, so
  `build/release.zig` ships x86_64 only.
- Windows: upstream's `WindowsWatcher.zig`/`wuffs.zig` do not compile on released
  Zig 0.16.0.

There is deliberately no architecture substitution and no Rosetta path. Loading
the x86_64 binary on an arm64 host would make an emulated build indistinguishable
from a native one — slower, with a different `process.arch` inside every tool the
binary shells out to, and no signal in the output. The npm package already
refuses for exactly this reason; a second channel that quietly does otherwise
would make "which install did you use?" a debugging question.

**Integrity.** `SHA256SUMS` is downloaded from the release and both the target
archive and `runtime.tar.xz` are verified *before* anything is extracted. The
digest tool is `sha256sum`, else `shasum -a 256`, else `openssl dgst -sha256`;
if none is present the install fails rather than proceeding unverified.

**Preflight.** `curl`, `tar`, and — on macOS, whose asset is a zip — `unzip` are
checked up front, and a missing one fails naming the tool and the package that
provides it. Checking up front rather than at the point of use means a host
missing `unzip` is told so before it has downloaded 30 MB.

**Bun.** Skipped entirely when `bun` is already on `PATH`. Otherwise the pinned
build is downloaded from `oven-sh/bun` releases into the install's private `bun/`
directory. The pin is an exact version (`1.2.23`); `mise.toml` pins `bun = "1.2"`,
which is a range and cannot be turned into a download URL. A gate asserts the
installer's pin still satisfies the `mise.toml` range, so the two cannot drift.

**ZigBase.** Skipped when `zigbase` is on `PATH` or the pinned version is already
cached. Otherwise the installer performs the same curl → `SHA256SUMS` → verify →
`tar --strip-components=1` sequence that `src/cli/zigbase.zig` performs, into the
same cache path, so the binary finds it through its ordinary step-3 lookup and
learns nothing new. Doing it at install time only moves the fetch off the
critical path of the first `dev`; a gate asserts the pinned version matches
`zigbase.zig`.

**Interface.**

| Flag | Environment | Meaning |
| --- | --- | --- |
| `--version <tag>` | `ZIGAPAGOS_VERSION` | Install this release instead of the newest. |
| `--prefix <dir>` | `ZIGAPAGOS_INSTALL_DIR` | Data root. Default `$XDG_DATA_HOME/zigapagos`. |
| `--bin-dir <dir>` | `ZIGAPAGOS_BIN_DIR` | Where the shim goes. Default `~/.local/bin`. |
| `--no-bun` | | Never install a private Bun. |
| `--no-zigbase` | | Never prefetch ZigBase. |
| `--base-url <url>` | `ZIGAPAGOS_INSTALL_BASE_URL` | Where release assets are fetched from. |
| `--help` | | Usage. |

`--base-url` exists so the test suite can run a real end-to-end install against a
fixture release on the local filesystem. An installer whose download path is only
ever exercised against the live internet is an installer with no tests.

**Idempotence.** Re-running installs into a fresh `versions/<tag>/` and flips
`current`. Installing an older tag after a newer one is a downgrade, not an
error. Nothing is deleted; old version directories are left for the user to
remove.

**PATH advice.** If the bin directory is not on `PATH`, the installer prints the
single `export` line to add and names the shell profile to add it to. It does not
edit the profile itself.

## Documentation surfaces

The one-liner is the headline in three places:

```sh
curl -fsSL https://valthon.github.io/zigapagos/install.sh | sh
```

- **`site/content/download.smd` / `site/layouts/download.shtml`** — a new
  "Install" section above "Build from source", which becomes the third option
  rather than the first.
- **`README.md`** — a new `## Install` section above Quickstart, with npm and
  from-source below it.
- **`docs/runtime-dependencies.md`** — the "what each distribution gives you"
  table gains an `install.sh` column. That table is checked by
  `tests/meta/runtime-deps-doc.sh`, so the new column is checked too.

**Serving the script.** `install.sh` is added to `static_assets` in
`site/zigapagos.ziggy`, and `site/build.sh` copies the repository-root canonical
into `site/assets/install.sh` as a **gitignored build artifact** — the pattern
`gen-docs-mirror.ts` already establishes for the docs mirrors. A committed second
copy under `site/assets/` would be a copy that can drift from the one users are
told to trust.

## Tests

A new `tests/install/` directory, picked up by CI's `tests/*/*.sh` glob:

- `syntax.sh` — `sh -n` and, when available, `shellcheck`.
- `install.sh` — a hermetic end-to-end install against a fixture release
  assembled on disk and passed via `--base-url`: asserts the layout, the
  generated shim, that `ZIGAPAGOS_RUNTIME_DIR` reaches the binary, and that a
  site with an island actually builds through the installed tree.
- `platforms.sh` — aarch64 and Windows hosts are refused, with the documented
  reason in the message.
- `preflight.sh` — each missing dependency (`curl`, `tar`, `unzip`, every digest
  tool) fails naming that tool.
- `integrity.sh` — a corrupted archive is fatal and leaves nothing installed.
- `idempotence.sh` — a second install of a different tag flips `current` and
  leaves the first version directory intact.
- `pins.sh` — the drift gates: the installer's Bun pin satisfies `mise.toml`'s
  range, and its ZigBase pin equals `src/cli/zigbase.zig`'s `pinned_version`.

Every regression test is verified to fail without the change it pins.

## Out of scope

- **arm64 support.** It is a `build/release.zig` matrix problem gated on the Zig
  0.17 port, not an installer problem.
- **Windows.** Same.
- **An uninstaller.** Removing `~/.local/bin/zigapagos` and the data directory is
  two `rm`s, and documenting them is cheaper than shipping and testing a script.
- **Package managers** (Homebrew, AUR, nix). Separate distribution channels with
  their own review loops.
